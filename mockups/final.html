서비스 기획

무엇을 어떻게 계산하는가

개요

친구·가족끼리 차 한 대로 여행을 가면 운전은 대개 한 사람이 도맡습니다. 기름값과 통행료는 N분의 1로 나누지만, 서너 시간 운전한 사람의 노동은 “고마워” 한마디로 끝나는 경우가 많습니다.

이 앱은 도착지와 동승자만 넣고 출발한 뒤, 여행 중 탭 몇 번으로 남긴 기록(하차, 운전 교대, 결제, 괘씸)으로 실제 비용(유류비·통행료)과 운전 노동비를 계산해 사람별 정산 금액을 만들어 줍니다. 여기에 조수석에서 잠든 사람, 혼자 간식 먹은 사람을 반영하는 괘씸모드를 더해 정산을 대화거리로 만듭니다.

목표
  • 운전자의 노동을 “시간 × 기준 단가” 또는 “택시였다면 들었을 기사 몫”이라는 납득 가능한 숫자로 보여준다.
  • 중간 합류·하차, 운전 교대가 있어도 구간 단위로 공정하게 나눈다.
  • 기름값은 실제 조회 시점 시세, 직접 주유했다면 해당 주유소 단가를 쓴다.
  • 한 사람의 폰에서 입력과 계산을 끝내고, 정산 결과는 링크 하나로 공유한다.
주요 사용자

차를 가진 20~40대 운전자(정산 요청자)와 그 동승자. 주말 국내 여행, 명절 귀성, 캠핑·골프 모임 등.

입력 방식

여행 한 건은 입력 담당 한 명의 폰에서만 기록하고 계산합니다. 로그인과 회원가입은 없고, 다른 멤버는 공유받은 결과 링크만 봅니다. 출발 전 입력은 도착지와 동승자 2개뿐이고, 구간·운전자·좌석은 여행 중 탭 기록에서 자동으로 만들어집니다. 나머지는 기본값으로 계산하고, 고치고 싶은 값만 결과 화면에서 고칩니다.

계산 로직

구간 자동 생성

사용자는 구간을 만들지 않습니다. 여행 중 누른 기록으로 앱이 구간을 만듭니다.

운전 시간 = 도착 탭 시각 − 출발 탭 시각 − 휴식 합계 여행 경로 = 출발지 → 도착지 1회 조회 (거리, 예상 시간, 통행료, 택시요금) 구간 경계 = 하차 · 합류 · 운전 교대 기록 시각 구간 거리 = 여행 거리 × (구간 운전 시간 ÷ 전체 운전 시간)
  • 하차·합류 장소를 고르면 그 지점을 경유지로 재조회해 비율 추정 대신 실제 경로 거리를 쓴다.
  • 통행료는 결제 기록이 있으면 그 금액, 없으면 경로 조회값을 구간 거리 비율로 배분한다.
  • 실제 운전 시간이 예상의 1.3배를 넘으면 정체인지 우회인지 앱이 판단할 수 없으므로, 결과 화면에 “경로보다 멀리 돌았나요? 거리 고치기”를 표시한다. 자동으로 거리를 늘리지 않는다.
  • 좌석은 묻지 않는다. “조수석 수면”을 누르면 그 사람을 조수석으로 자동 지정하고, 택시모드는 좌석 변경으로 뒷자리를 표시했을 때만 적용한다.

유류비

차량 연비는 기본값 12km/L로 시작하고, 결과 화면에서 한 번 고치면(직접 입력 또는 차종 공인연비) 다음 여행부터 기억합니다. 공인연비에는 보정계수(도심 0.85, 고속도로 1.1)를 적용합니다.

구간 연료량(L) = 구간 거리(km) ÷ 연비(km/L) 구간 유류비 = 구간 연료량 × 적용 단가

적용 단가는 다음 순서로 정합니다.

  • 주유 기록 없음: 여행 조회 시점의 출발지 시·도 평균가(유종별). 조회 시각과 단가를 스냅샷으로 저장해 나중에 다시 계산해도 값이 바뀌지 않게 한다.
  • 주유 기록 있음: 주유 이후 구간은 해당 주유소 단가. 정밀 모드에서는 탱크 잔량 기준 가중평균을 쓴다.
정밀 모드 단가 = (잔량 × 기존 단가 + 주유량 × 주유 단가) ÷ (잔량 + 주유량)

통행료·주차비

통행료는 경로 API 값을 기본으로 하고 실제 영수증 금액으로 수정할 수 있습니다. 하이패스 할인(출퇴근·경차 등)은 수동 수정. 주차비는 발생 구간의 도착 지점에 붙여 해당 구간 탑승자가 나눕니다.

측정 한계와 보완

  • 조회 시점 교통: 경로 API의 교통 상태는 조회한 순간의 정보라 실제 주행과 다를 수 있다. 도착 후 입력하는 실제 운전 시간 비율을 주 지표로, API 값은 입력 전 예상용 보조로 쓴다.
  • 공공 교통 이력은 계산이 아니라 검증에 쓴다 (2차): 실제 운전 시간 비율은 그 사람이 그날 겪은 정체를 직접 반영하므로 도로 평균인 공공 데이터보다 정확하다. 공공 데이터는 입력한 운전 시간이 그럴듯한지 확인하는 용도로만 쓴다(어뷰징 대응 10번).
  • 출발 시각 기준 예측 (2차): 카카오모빌리티 “미래 운행 정보 길찾기”로 출발 예정 시각의 교통을 예측한다. 일 5,000건 무료이며 일일 하드 상한에 포함한다.
  • 사람이 입력한 값: 운전 시간은 출발·도착 탭으로 자동 기록되어 조작 여지가 작다. 결과 화면에서 직접 고친 값과 기상·체감 점수에만 “직접 입력” 표시와 원래 값을 보여준다.
  • 폰 센서 (2차, 보상 미반영): GPS 정차·출발 반복, 가속도 기반 주행 기록은 폰 안에서만 계산해 운전자 본인 기록으로만 보여준다. PWA는 화면이 켜진 동안만 측정되고 거치 위치에 따라 값이 크게 달라져 정산에는 쓰지 않는다.

택시비 비교

결과 화면에 “택시로 갔다면 총 얼마, 운전자 덕분에 아낀 금액 얼마”를 보여줍니다. 계산 자체에 쓰이지 않아도 운전자의 수고를 체감하게 하는 장치입니다.

아낀 금액 = Σ 구간 택시 예상요금 − (Σ 공통비 + Σ 노동비)

분담 공식

구간 s에서 탑승자 수를 N(운전자 포함), 비운전 탑승자를 i라고 할 때:

i의 공통비 분담 = 구간 공통비 ÷ N i의 노동비 분담 = (구간 노동비 ÷ (N − 1)) × i의 괘씸 배수 운전자의 공통비 분담 = 구간 공통비 ÷ N (운전자도 탑승자라서 낸다) 운전자가 받는 금액 = Σ 비운전 탑승자의 노동비 분담

괘씸 배수는 가산형이 기본입니다. 괘씸한 사람이 더 낸 만큼 운전자가 더 받고, 착한 동승자의 부담은 그대로입니다. 설정에서 재분배형(노동비 총액은 고정, 괘씸한 사람 비중만 커짐)으로 바꿀 수 있습니다.

마지막으로 “실제로 결제한 사람”(대부분 차주)을 기준으로 멤버 간 송금 목록을 만듭니다. 금액은 원 단위 정수로 계산·표시합니다. 나눗셈에서 생기는 1원 미만은 반올림하고, 반올림으로 생긴 차이는 운전자 몫에서 흡수해 차액 합계가 항상 0이 되게 합니다.

괘씸모드

구간마다 멤버별 괘씸 점수를 쌓고, 점수를 배수로 바꿔 노동비 분담에 곱합니다.

괘씸 배수 = 1.0 + 0.1 × 구간 괘씸 점수 (점수 0~10, 배수 1.0~2.0)

택시 느낌은 살리되 다른 괘씸 규칙과 같은 상한(2.0배)을 지킵니다. 서울 → 원주를 둘이 갔고 동승자가 뒷자리에 앉았다면 택시형 금액은 (140,000 − 22,000) × 30% = 35,400원이지만 상한 30,960원(15,480 × 2.0)이 적용됩니다. 영수증에는 “택시였다면 기사님께 35,400원, 친구라서 30,960원”으로 표시합니다.

점수는 0 아래로 내려가지 않습니다. 감면으로 배수가 1.0보다 작아지지 않게 해서 “착한 행동으로 돈 버는” 역효과를 막습니다.

인정 방식

  • 기록은 입력 담당 폰에서 한다. 동승자가 말로 알려주면 입력 담당이 버튼으로 남기고, 입력 담당이 운전 중이면 도착 후 몰아서 기록한다.
  • 기본은 기록 그대로 반영한다. 이의가 있으면 도착 요약의 “괘씸 N건 보기”에서 체크를 해제한다(필수 단계 아님).
  • 운전자는 확인 화면에서 “용서하기”로 개별 항목을 지울 수 있다.
  • 잘못 누른 기록은 토스트의 “취소”(5초) 또는 타일 길게 누르기(−1)로 되돌린다.
  • 결과 영수증에는 인정된 괘씸 사유가 선택한 말투로 한 줄씩 찍힌다.

감수하는 점

  • 경유지를 미리 넣지 않아 경로 조회는 출발지→도착지 한 번이다. 크게 돌아간 여행은 거리가 짧게 잡힐 수 있어 결과 화면에서 거리 고치기를 안내한다.

  • 구간마다 경로를 조회하지 않아 카카오 API 호출이 줄어, 0원 운영에는 유리하다.

비용

Cloudflare 공식 문서(2026년 9월 확인) 기준 Workers 무료 플랜은 하루 10만 요청, 요청당 CPU 10ms이고, fetch 호출이나 KV 읽기를 기다리는 시간은 CPU 시간에 포함되지 않습니다. 이 앱의 Worker는 외부 API를 기다리는 시간이 대부분이라 CPU 한도에 걸릴 일이 적습니다. 정적 자산 요청은 무료이고 무제한이라 결과 페이지 조회는 요청 수에 들어가지 않고, Cron Trigger는 무료 플랜에서 계정당 5개까지라 유가 갱신 1개면 충분합니다. 유료 플랜은 월 최소 5달러입니다.

여행 한 건에 장소 검색·경로·유가 조회로 대략 15회 안팎의 요청을 쓴다고 보면 무료 한도로 하루 수천 건을 처리할 수 있습니다. 실제 병목은 Cloudflare보다 카카오모빌리티 길찾기 무료 호출량일 가능성이 높습니다(구간 수만큼 호출).

개발 초기에 확인할 위험

  • 오피넷 API가 Cloudflare 해외 경유 IP의 호출을 막지 않는지 첫 주에 실제 호출로 확인. 막히면 유가 갱신만 국내 소형 서버나 GitHub Actions 예약 작업으로 옮긴다.
  • 카카오모빌리티에 결제수단이 없을 때 무료량 초과분이 차단되는지 청구되는지(확인 전까지 하드 상한으로 방어).
  • Rate Limiting 바인딩의 무료 플랜 사용 가능 여부.
  • 오피넷 API 키의 일일 호출 제한과 서비스 이용 조건.
  • 오피넷 KATEC 좌표 변환 정확도(주변 주유소 기능, 2차).

개발 규칙

  • Worker 코드에서 요청 본문, 쿼리, 좌표를 console.log로 출력하지 않는다. 코드 리뷰 체크 항목.
  • Workers 로그는 끄거나 오류 코드만 남기도록 설정한다.
  • 운전 중 잠금(S8)의 속도 감지는 폰 안에서만 계산한다.
  • 서버 기반 음성 인식을 쓰지 않는다. 음성이 외부 회사 서버로 전송되기 때문이다.
  • 광고 스크립트는 정산 결과 화면(S10)의 광고 카드에서만 불러오고 결과 보기 페이지(/r)에는 넣지 않는다. 광고 요청에 이름·금액·목적지 같은 여행 정보를 넣지 않는다.
  • 분당 호출 제한에는 IP를 키로 쓰지만 Cloudflare 제한 기능 안에서만 쓰이고 우리 저장소에 남기지 않는다.
  • 외부 API(카카오, TMAP, 오피넷)는 Worker의 IP만 보게 되어 사용자 IP가 외부 회사에 전달되지 않는다.

로그인이 없고 서버가 공개 API를 중계하는 구조라, 누구든 앱 없이 Worker를 직접 두드릴 수 있습니다. 목표는 완벽한 차단이 아니라 “공격해도 돈이 나가지 않고, 정상 사용자는 수동 입력으로라도 정산을 끝낼 수 있게” 만드는 것입니다.

요청이 거치는 방어 순서

비용이 싼 검사를 앞에, 비싼 검사를 뒤에 둡니다. 앞 단계에서 거절되면 뒤 단계(DO 호출, 카카오 호출)는 실행되지 않습니다.

① 경로·메서드·입력값 검증 (CPU만 사용) ② 세션 토큰 서명·만료 확인 (CPU만 사용) ③ 차단 목록 확인 (KV 읽기) ④ 분당 호출 제한 (Rate Limiting 바인딩) ⑤ 응답 캐시 확인 → 적중 시 반환 (Cache API) ⑥ 일일 예산 차감 (Durable Object) ⑦ 카카오 호출 → 응답 축소 → 캐시 저장

1. 세션 발급: 사람이 쓰는 앱인지 확인 (T1, T2)

  • 앱을 처음 열 때 Turnstile(보이지 않는 모드)을 실행하고, 토큰을 POST /api/session으로 보낸다.
  • Worker는 Turnstile 검증에 통과하면 세션 ID, 만료 시각(2시간)을 HMAC으로 서명한 토큰을 준다. 이후 모든 /api 요청은 이 토큰이 필요하다.
  • 토큰 검증은 서명 계산만 하므로 외부 호출 없이 끝난다. 위조·만료 토큰은 ②에서 즉시 401.
  • 세션 발급 자체도 IP당 10분에 5회로 제한해 세션 대량 생성을 막는다.
  • Turnstile 위젯 호스트에는 서비스 주소만 등록하므로, 다른 사이트에 위젯을 심어 세션을 받아가는 방식은 통하지 않는다.

4. 훔쳐 갈 가치 낮추기 (T2)

  • 응답 축소: 경로 응답은 구간별 거리·시간·통행료·택시요금과 난이도용 비율 2개, 숫자 6개만(2차에 고속도로 노선명·거리 추가, 개인 정보 아님). 비율은 Worker가 도로별 교통 정보로 계산한 뒤 원본을 버린다. 경로 좌표(vertexes), 도로별 정보는 내보내지 않는다. 내비·배달 서비스가 대신 쓰기에 쓸모없게 만든다.
  • 장소검색 축소: 상위 5개, 이름·주소·좌표만. 전화번호·카테고리·페이지 넘김은 제공하지 않는다.
  • 입력 제한: 좌표는 대한민국 영역 안, 지점 최대 11개(구간 10개), 검색어 2~40자. 벗어나면 400.
  • 캐시: 좌표를 소수점 4자리(약 10m)로 반올림한 뒤 비밀 값과 섞어 해시한 값을 캐시 키로 사용. 같은 구간 반복 조회는 카카오를 부르지 않는다.

5. Worker 요청 한도 방어 (T3)

  • 거절 경로(①~④)는 외부 호출 없이 1ms 안에 끝나게 유지해 CPU 한도에 걸리지 않게 한다.
  • Worker 요청 한도가 소진돼도 서비스가 멈추지 않게 설계한다. 앱 화면은 서비스 워커로 폰에 캐시되고, 계산·기록·결과 링크 생성은 서버 없이 동작한다. 결과 보기 페이지도 브라우저에서만 해석한다.
  • 정적 자산은 Worker 코드보다 먼저 응답하도록 설정한다. 요청 한도 소진 시 정적 자산 응답이 유지되는지는 배포 후 실제로 확인한다.
  • 도메인을 사게 되면(수익 발생 후) Worker 실행 전 단계인 WAF 차단 규칙으로 옮겨 요청 수 소모 자체를 줄인다.

6. 감시와 비상 스위치 (T1~T4, T7)

  • 알림: Cron이 매시 정각 Durable Object 카운터를 읽어 사용률 50%, 80%, 95%에서 디스코드 또는 텔레그램 웹훅으로 알림(무료).
  • 이상 징후: 세션 하루 한도에 닿은 세션 수를 알림에 포함. 한도에 닿는 세션이 10개를 넘으면 공격 의심 알림. IP는 저장하지 않으므로 공격자별 분석은 하지 않는다.
  • 비상 스위치: KV에 auto_route, auto_places 켜기/끄기 값. 재배포 없이 대시보드에서 바로 끈다.
  • 차단 목록: KV에 세션 ID, 그날만 쓰는 솔트로 해시한 IP. 수동 등록만 하고 당일에 만료. KV 쓰기 한도에 걸리지 않는다.
  • 키 유출 대응: 카카오·오피넷 키 재발급 → wrangler secret put으로 교체 → 옛 키 폐기. 절차를 운영 문서에 적어 둔다.

7. 제공자 운영정책 지키기 (T4)

  • 카카오 앱은 하나만 만든다. 개발용·운영용으로 앱을 나누거나 쿼터를 늘리려 앱을 추가하지 않는다(동일 서비스 복수 앱 운영은 차단 사유).
  • 개발·테스트는 저장해 둔 샘플 응답(목업 데이터)으로 하고, 실제 키 호출은 통합 테스트 때만.
  • 일일 하드 상한을 카카오·TMAP 무료량보다 낮게 둬서 쿼터 초과 이용이 구조적으로 발생하지 않게 한다.
  • 카카오 앱이 차단되더라도 TMAP 예비로 전환되어 서비스가 멈추지 않는다. TMAP도 계정·앱을 하나만 운영한다.

8. 결과 링크 악용 막기 (T5)

  • 형식 검증: 링크 데이터 최대 4KB, 압축 해제는 32KB에서 중단. 멤버 10명, 구간 10개, 이름 10자, 금액 0~500만원 범위를 벗어나면 “손상된 링크” 화면.
  • 자유 텍스트 최소화: 괘씸 사유는 항목 코드로만 전달하고 문구는 페이지가 가진 고정 문장으로 표시. “기타” 항목의 메모는 링크에 넣지 않는다. 자유 입력은 이름뿐이다.
  • 안전한 표시: 모든 값은 텍스트로만 출력(HTML 해석 금지). 링크 데이터 안의 URL은 절대 링크로 만들지 않는다. 결과 페이지에 엄격한 CSP 적용.
  • 송금 유도 차단: 결과 링크에는 계좌번호 원문을 절대 넣지 않는다. 송금 버튼은 토스 아이디 링크, 카카오페이 송금 링크처럼 정해진 형식의 주소만 허용하고, 결과 페이지가 표시 전에 형식을 다시 검증한다. 버튼 옆에 “송금 앱에서 받는 사람이 ○○ 님인지 확인하세요”를 둔다. 결과 페이지 고정 문구: “유가 시세, 최저시급, 함께 확인한 괘씸 기록으로 자동 계산했어요. 금액은 링크를 만든 사람이 입력한 값 기준이니 송금 전에 확인하세요.” 입력 담당의 부담을 덜면서 사실과 어긋나지 않게 한다.
  • 서명은 하지 않는다: 서명하려면 결과 내용이나 해시를 서버로 보내야 해서 서버 최소 정보 원칙에 어긋난다. 서명은 “앱에서 계산했다”는 증명일 뿐 입력값이 사실이라는 증명도 아니므로, 고정 안내 문구로 대신한다.

9. 정산 조작 드러내기 (T6)

한 폰 입력 구조에서는 입력 담당이 값을 바꾸는 것을 막을 수 없습니다. 대신 결과에서 보이게 합니다.

  • 자동 조회값을 직접 수정한 항목은 결과 영수증 계산 근거에 원래 값과 함께 표시. 예: “운전 시간 직접 입력: 예상 1시간 → 2시간”
  • 직접 입력한 운전 시간이 자동 조회 예상의 1.5배를 넘으면 결과 페이지에 주의 표시. 조회 시점 교통 기준이라 부정확할 수 있어, 고속도로 구간은 2차에서 10번의 평소 이력 기준 판정으로 대체한다.
  • 괘씸 배수 상한 2.0, 난이도 계수 상한 2.0 유지. 직접 입력한 실제 운전 시간·기상·체감 점수는 영수증에 “직접 입력”으로 표시. 결과에 택시 예상요금을 함께 보여줘 비상식적인 금액이 한눈에 드러나게 한다.

10. 공공 교통 이력으로 운전 시간 검증하기 (T6, 2차)

“금요일 저녁이라 막혔다”는 입력이 사실에 가까운지, 동승자가 판단할 근거를 줍니다. 서버는 여행 시각을 전혀 알지 못하고 비용도 들지 않습니다.

  1. 이력 수집 (GitHub Actions)주 1회 예약 작업이 한국도로공사 VDS 소통 통계를 받아 “고속도로 노선 × 방향 × 요일 × 시간대 → 평소 평균 속도, 정체 빈도” 요약표(JSON)를 만든다. 원본은 크고 무거우므로 Worker에서 처리하지 않는다.
  2. 정적 배포요약표를 Worker 정적 자산으로 배포한다. 폰은 필요할 때 한 번 내려받아 캐시한다.
  3. 노선 정보 받기/api/route가 구간마다 지나는 고속도로 노선명과 노선별 거리를 추가로 돌려준다. 카카오 응답의 도로 이름으로 Worker가 계산하고 원본은 버린다.
  4. 폰 안에서 비교폰이 출발 시각과 노선으로 요약표를 조회해 “평소 이 시간대 예상 소요 시간”을 계산한다. 시각은 서버로 가지 않는다.
  5. 결과에 표시입력한 실제 운전 시간과 평소 예상을 나란히 보여준다.
판정조건결과 영수증 표시
평소 혼잡 시간대입력 시간이 평소 예상의 1.3배 이내“금요일 저녁 영동고속도로는 평소에도 느린 시간대예요. 입력한 운전 시간과 비슷해요.”
평소보다 오래 걸림평소 예상의 1.3~2배“평소보다 오래 걸렸어요. 사고·공사·날씨 영향일 수 있어요.” (중립)
확인 필요평소 예상의 2배 초과확인 필요 “평소 이 시간대의 2배 넘게 걸렸다고 입력됐어요.”
판정 불가고속도로 비중이 구간 거리의 50% 미만, 요약표에 없는 노선표시하지 않음
  • 판정은 정산 금액을 바꾸지 않는다. 금액은 입력값 그대로 계산하고 판단은 사람에게 맡긴다.
  • “확인 필요”도 비난하는 문구를 쓰지 않는다. 실제 사고나 폭설은 이력 평균으로 설명되지 않는다.

정책과 예외 처리

  • 안전: 입력 담당이 현재 구간 운전자로 지정되어 있고 이동 속도가 감지되면 입력을 막고 “도착 후 기록하세요”를 띄운다. 속도 계산은 폰 안에서만 한다.
  • 자동 조회 한도 도달: 화면을 막는 팝업 대신 입력 필드 위 안내 문구와 수동 입력 필드 자동 펼침. 차 안에서 쓰는 앱이므로 흐름을 끊지 않는다.
  • 운전 교대: 여행 중 “운전 교대” 버튼으로 새 운전자를 탭하면 그 시각에 구간이 나뉜다. 깜빡했으면 도착 후 타임라인에서 추가한다.
  • 앱을 못 켠 여행: 홈의 “빠른 정산”에서 도착지·인원·출발/도착 시각만으로 정산한다. 괘씸·결제 기록은 결과 화면에서 추가할 수 있다.
  • 차주가 운전하지 않는 경우: 노동비는 운전자에게, 차량 감가(P2)는 차주에게 따로 지급.
  • 연비 모름: 차종 공인연비 사용, 주유 기록이 2회 이상 쌓이면 실측 연비 제안.
  • 유가 API 장애: 마지막 성공 스냅샷 사용, 결과에 “기준 시각”을 명시.
  • 괘씸모드 과열 방지: 배수 상한 2.0, 한 사람이 받는 괘씸 가산액이 본인 기본 노동비 분담액을 넘지 않게 제한. 여행 생성자가 끌 수 있음.
  • 재계산: 입력을 수정하면 즉시 재계산. 결과 링크는 발급 시점 결과를 담으므로, 확정 후 수정하면 새 링크를 다시 공유한다. 결과 페이지에 발급 시각을 표시해 옛 링크와 구분한다.
  • 중간 하차·합류: 여행 중 “하차·합류” 버튼으로 사람과 시각만 폰에 기록한다. 도착 후 타임라인에서 그 시각을 경계로 구간이 나뉘고, 장소는 검색으로 고르거나 고르지 않으면 운전 시간 비율로 거리를 나눈다. 지도 핀이나 현재 위치는 쓰지 않는다.
  • 선결제: 동승자가 휴게소에서 기름값·통행료를 냈다면 결제 기록에 결제자로 남긴다. 정산은 사람별 “낸 돈 − 자기 몫”으로 차액을 계산해 최소 송금 목록을 만든다.
  • 폰 분실·앱 삭제: 서버에 기록이 없으므로 복구되지 않는다. 여행 내보내기(파일 백업)를 P1로 제공한다.

사용성을 지키는 장치

  • 결과가 먼저: 광고를 기다리는 대기 화면, 카운트다운, 전면 광고를 쓰지 않는다.
  • 화면이 밀리지 않게: 광고 카드는 콘텐츠 맨 끝에 붙기 때문에, 불러오는 순간에도 위의 금액·목록 위치가 움직이지 않는다.
  • 실수 클릭 방지: 광고 카드는 하단 “결과 링크 공유” 버튼과 겹치지 않도록 버튼 영역만큼 여백을 둔다. 광고 네트워크의 유도 클릭 금지 정책과도 맞다.
  • 닫으면 끝: ✕를 누르면 카드가 사라지고 이 여행에서는 다시 나오지 않는다.
  • 소리·움직임 없음: 자동 재생 동영상, 소리 나는 광고 형식은 쓰지 않는다. 야간 모드에서는 카드 테두리와 배경을 어둡게 한다.

광고 네트워크 현실 (확인 필요)

  • 웹에 맞는 형식: 결과 화면 안의 카드 광고는 웹(PWA)에서 쓸 수 있는 배너·네이티브 광고와 잘 맞는다. 카카오 애드핏은 배너·네이티브 광고를 제공하고, 실행·화면 전환 팝업 광고는 앱 전용 상품이다.
  • 매체 심사: 애드핏은 매체 소유관계, 콘텐츠의 질적·양적 품질, 트래픽 품질을 심사한다. 도구형 앱은 불리할 수 있어 서비스 소개·사용 가이드·계산 방법 설명 페이지를 함께 준비한다.
  • 도메인: 구글 애드센스는 상위 도메인 기준으로 승인받는 것이 일반적이라 workers.dev 주소로는 어려울 가능성이 높다. 자체 도메인 구입(연 1만 원대)이 첫 지출이 될 수 있다.
  • 닫기 버튼과 노출 기준: 광고 카드에 닫기 버튼을 두는 것과 화면 맨 아래 배치가 광고 네트워크 정책·노출 집계 기준에 맞는지 확인한다.

개인정보와 보안

  • 광고 스크립트는 S10의 광고 카드에서만 불러온다. 결과 보기 페이지(/r)는 CSP로 외부 스크립트를 막는다.

남은 확인 사항

  • 유상운송 (출시 전 필수): 기름값을 넘는 “운전 노동비” 정산을 돕고 광고 수익을 내는 서비스가 여객자동차운수사업법상 유상운송 알선으로 해석될 여지가 있는지 법률 확인. 영수증 표현은 “요금”이 아닌 “수고비”로 통일.
  • 광고 (출시 전): 카카오 애드핏 매체 심사 기준(도구형 앱의 콘텐츠 품질), 구글 애드센스의 도메인 조건, 광고 카드 닫기 버튼·하단 배치의 정책 적합성, 개인정보처리방침의 광고 관련 고지와 맞춤형 광고 동의 필요 여부, 광고 수익 소득 신고.
  • 송금 링크 (출시 직후 기능 전): 토스·카카오페이 송금 링크의 형식, 금액 자동 입력 지원 여부.
  • 위치정보법 (출시 전 필수): 운전 중 잠금의 폰 내부 속도 감지와, 사용자가 고른 장소 좌표를 서버가 중계하는 것이 위치정보 수집·이용 신고나 동의 대상인지 전문가 확인. 해당하면 동의 화면 추가 또는 기능 조정.
  • 기술 확인: “개발 초기에 확인할 위험” 목록(오피넷 해외 IP 차단 여부, 카카오모빌리티 결제수단 없을 때 초과분 처리, Rate Limiting 바인딩 무료 플랜 사용 가능 여부, 오피넷 이용 조건).
  • TMAP 예비 (개발 착수 전): Free 요금제를 결제수단 없이 쓸 수 있는지, 응답 캐시·가공 표시 허용 범위(카카오 포함), 도로별 교통 정보를 받는 방식.
  • 공공 교통 이력 (2차 착수 전): 한국도로공사·교통 빅데이터 플랫폼 데이터의 이용허락 범위(서비스 내 가공 표시 가능 여부), 자동 다운로드 허용 여부, 카카오 도로 이름과 도로공사 노선명 매칭 정확도.
